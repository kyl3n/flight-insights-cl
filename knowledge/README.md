# Knowledge pack

Versioned data the engine reads, updatable without an app release (spec: System architecture). Everything here is generated by the tools in `tools/` from ArduPilot's own sources, except the curated rules, which say why they exist.

| Path | What it is | Made by |
| --- | --- | --- |
| `manifest.json` | Which releases the pack covers, and the ArduPilot commit each came from | `tools/build_param_metadata.py` |
| `params/<version>/copter.json.gz`, `plane.json.gz` | Every parameter of a release: name, display name, description, units, range, values, bitmask, user level and flags (reboot required, read-only, volatile, calibration). Copter includes helicopters, Plane includes QuadPlanes. | `tools/build_param_metadata.py`, which runs ArduPilot's `param_parse.py` |
| `params/renames.json` | Parameters renamed between releases, each with its proof | `tools/find_renames.py` |
| `params/beyond_range.json` | Parameters whose firmware accepts values past the documented range (`FS_DR_TIMEOUT`: documented 0 to 120, stored in 16 bits with no upper limit), each with the source lines at every release it names | Curated from the firmware source |
| `params/classes.json` | How parameters are classed: tuning, calibration, learned, counter, hardware, ground station | Curated |
| `boards/<version>.json` | Every ChibiOS board's logged short name with its MCU, MCU family (F4, F7, H7...) and bootloader board ID | `tools/build_boards.py`, from the release's `hwdef` files and `board_types.txt` |
| `setup/platform.json` | The guided platform setup: its ten steps and every field, in English and Ukrainian, each saying why it is asked and, if required, what a gap prevents | Curated |
| `rules/archetypes.json` | Rule pack v0 for the archetype scorer: weighted conditions on fingerprint features, each with its reason; marked uncalibrated | Curated |
| `rules/hover.json` | When a multirotor, helicopter or QuadPlane in VTOL flight counts as hovering steadily; starting values, marked uncalibrated | Curated |
| `options/copter.json` | The Better options catalog: for each option, when the aircraft is set up the weaker way, the better choice and its parameter changes, what it needs (facts the engine works out), its benefit by mission priority, its cost, its sources, and its wording in English and Ukrainian; plus the questions that settle unknown facts, each tied to a platform setup field | Curated |
| `options/coverage.json` | Every configurable subsystem with the options that cover it; a subsystem with none is shown as not yet covered | Curated |
| `rules/filters.json` | The filter candidate search: the lag frequency, the noise band and target, the low-pass cutoffs and bandwidths tried, notch limits per board class, when the processor counts as busy, and how much better a candidate must be; starting values, marked uncalibrated | Curated |
| `rules/logging.json` | Which log messages the analyzers need and which `LOG_BITMASK` bits log them, per vehicle, plus the `INS_RAW_LOG_OPT` bits; each read from the named release's source | Curated |
| `rules/recommend.json` | The recommendation engine: per-flight step limits for gains (uncalibrated), the changes never proposed automatically, risk and test-flight verification per stage, expected effects, and the wording of every reason, in English and Ukrainian | Curated |
| `rules/audit.json` | The parameter audit: which rate gains count as never tuned, the `FS_THR_VALUE` arming rule (cited from the firmware source), the cell-voltage bands that catch a setting made for another pack (uncalibrated), and which parameters are controller gains | Curated |
| `rules/trends.json` | Performance trends: how many good flights make an airframe's baseline, its percentile band, how many flights outside it count as drift, and the sparkline length; starting values, uncalibrated | Curated |
| `metrics/*.json` | The metric registry: every metric and finding the analyzers produce, with its definition, method, unit, direction, zones and their sources, and its wording in English and Ukrainian. The engine refuses an entry with any of that missing | Curated |
| `enums/<version>.json` | Flight-mode names per vehicle, log-event names, error subsystems and codes, and internal-error bits, by the numbers logs record (MODE.ModeNum, EV.Id, ERR.Subsys and ERR.ECode, PM.InE) | `tools/build_enums.py`, from the release's `mode.h`, `AP_Logger.h` and `AP_InternalError.h` |
| `frames/<version>.json` | Every multirotor frame the matrix mixer sets up, by `FRAME_CLASS` and `FRAME_TYPE`: each motor's roll, pitch, yaw and throttle factors after the mixer's own normalisation, and the frames only Plane builds (QuadPlane) marked so. The motor-out margin solves against them | `tools/build_motor_frames.py`, which replays each case of the release's `AP_MotorsMatrix.cpp` and refuses any construct it does not know; `tools/check_motor_frames_sitl.py` flies every SITL multirotor frame and checks each motor's fitted factors against the table |
| `ai/system.md` | The system prompt of every AI exchange: what Claude is given, what it is for, and how it must cite evidence and propose changes. Static text, the same for every flight, holding nothing about any aircraft | Curated |
| `logs/<version>.json.gz` | Every DataFlash log message a release can write, with each field's units and type: ArduPilot 4.7 writes a message's FMT only when it logs it, so no log shows them all. The location scrubber's rules are checked against these | `tools/build_log_messages.py`, which runs the release's `Tools/autotest/logger_metadata/parse.py` for Copter and Plane |
| `rules/scrubber.json` | The location scrubber's rules for the AI path: messages that hold a position and the few fields of each that may be read, messages blocked whole, location-revealing fields and units, ambient pressure and temperature to round, and the parameters removed from every packet, each with its reason | Curated |

## Adding a release

```sh
python3 knowledge/tools/build_param_metadata.py ~/ardupilot-4.7.3 4.7.3
python3 knowledge/tools/find_renames.py ~/ardupilot-4.7.2 ~/ardupilot-4.7.3 4.7.2 4.7.3
python3 knowledge/tools/build_enums.py ~/ardupilot-4.7.3 4.7.3
python3 knowledge/tools/build_log_messages.py ~/ardupilot-4.7.3 4.7.3
python3 knowledge/tools/build_boards.py ~/ardupilot-4.7.3 4.7.3
python3 knowledge/tools/build_motor_frames.py ~/ardupilot-4.7.3 4.7.3
uv run knowledge/tools/check_motor_frames_sitl.py --ardupilot ~/ardupilot-4.7.3 --version 4.7.3  # SITL built
```

`find_renames.py` records a rename only with proof from both releases' source: the old and the new name are stored in the same place in the parameter tables (same group, index and variable), so the value carries over unchanged. It lists every other removed or added parameter for review. A rescale, where the units change and the firmware converts the value, always needs a person. That person adds the entry by hand, with `scale` and an `evidence` that cites the conversion code. The engine's tests reject any entry without evidence.

## Licensing

The parameter metadata, the mode and event names and the board table are generated from ArduPilot's GPLv3 source (documentation comments, enums and board definitions), as ArduPilot does for ground stations. Shipping it with the app is on the spec's list of items for legal review.
